你已经拿到一份规格。这份规格应当关联着若干工单，描述如何实现该规格。

issue 跟踪器应当已经提供给你。如果没有，请告知用户运行 `/setup-matt-pocock-skills`。

目标是在一条**集成分支**上实现整份规格，并按照 issue 跟踪器收尾工作的方式解决每一张工单。

工单并非一份步骤清单。它们是一个带有阻塞关系的**任务图**。这意味着始终存在一批可以接手的**前沿工单（frontier）**。

每个子代理都应使用全新的上下文窗口启动。

与子代理之间的通信应当精简。主要通过**上下文指针**进行沟通：指向规格、工单、调研笔记以及先前的提交。不要重复指针已能提供的信息。

**实现者子代理**应在条件允许时于后台运行，以获得最大并发度。

## 步骤

1. 阅读规格与工单，理解任务图。

2.（可选）使用一个**探索子代理**完成工单所需的任何探查——相关的代码库文件或外部文档。确保探索子代理能够保存文件：它应将自己的 markdown 笔记保存在代码库之外的一个目录中，供未来所有子代理访问。这样可以让**实现者子代理**专注于实现，而非探查。

3. 创建集成分支。如果 issue 跟踪器通过 PR（拉取请求）收尾工作，或用户要求创建 PR，则在步骤 5 中首次合并之后开启一个草稿 PR（领先 main 且没有任何提交的分支无法开启 PR），将其标记为收尾该规格与工单。

4. 每张工单使用一个全新的**实现者子代理**，各自在独立分支上的独立工作树中工作。每个实现者子代理：
   - 开始前确认其工作树基于集成分支，若不是则重置到集成分支上；
   - 调用 Skill 工具并使用 `tdd` 来构建工单；
   - 在报告完成前，将集成分支的最新提交合并进自己的分支

5. 一旦某个**实现者子代理**完成，就用一个**合并者子代理**将其工作合并到集成分支。

6. 如果这改变了可接手工单的**前沿**，再启动更多**实现者子代理**处理新工单。这样可以实现最大并发度。

7. 全部工单完成后，调用 Skill 工具并使用 `code-review`，在集成分支上进行代码评审。在一个全新的**实现者子代理**中修复代码评审提出的所有问题。

8. 如果存在草稿 PR，将其标记为可评审。否则，按照 issue 跟踪器收尾工作的方式解决每张工单，并汇报集成分支。

9. 清理所有**实现者子代理**的工作树。
