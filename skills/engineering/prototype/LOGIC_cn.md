# 逻辑原型

一个独立自包含的 HTML 文件（一份**可分享的演示**），任何人都可以通过点击按钮来驱动一个状态模型。当问题关乎**业务逻辑、状态流转或数据形态**时使用：这类东西在纸面上看起来合理，但只有拿真实案例推一遍之后才会觉得不对劲。

因为它是单文件、无需安装，你可以把它交给非开发人员（设计师、PM、领域专家），让他们自己感受这个模型。所以它要说他们的语言，而不是代码的语言。

## 何时适合采用这种形态

- 「我不确定这个状态机能否处理先 X 后 Y 的边界情况。」
- 「这个数据模型到底能不能表达……这种情况？」
- 「我想在动手写 API 之前，先感受一下它应该长什么样。」
- 任何有人想**按按钮、看状态变化**的场景。

如果问题是「这应该长什么样」，那这条分支选错了。请使用 [UI.md](UI.md)。

## 流程

### 1. 明确问题

写代码之前，先写下你要原型化的是什么状态模型、要回答什么问题。一段话，放在演示顶部（放在可见的引言里，而不只是一条注释）。一个回答了错误问题的逻辑原型纯属浪费，所以要把问题写清楚，方便之后核对——无论用户是当下在看，还是之后 AFK 回来再看。

### 2. 把逻辑隔离到一个可移植的模块里

把真正的逻辑（回答问题的那部分）放进单个 `<script>` 块，写成一个小巧、纯粹的模块，日后可以整体抽出来放进真实代码库。围绕它的页面是一次性的；这个模块不是。

合适的形态取决于问题：

- **纯 reducer**：`(state, action) => state`。适合动作是离散事件、状态为单一值的情况。
- **状态机**：显式的状态与流转。适合「当下哪些动作甚至是合法的」本身就是问题一部分的情况。
- **一组作用于普通数据类型的纯函数**。适合没有隐含的当前状态、只有变换的情况。
- **一个方法边界清晰的类或模块**，当逻辑确实持有持续的内部状态时使用。

选择最贴合所提问题的形态，*而不是*最容易接到页面上的那个。保持纯粹：不碰 DOM，不碰 `document`，不让按钮处理器伸进模块内部。页面调用模块；数据不向反方向流动。这正是原型在自身生命周期结束后仍有价值的原因：问题一旦得到回答，经过验证的 reducer / 状态机 / 函数集可以直接提升到真实模块中。

### 3. 构建可分享的 HTML 文件

单文件，纯 HTML/CSS/JS：不用框架、不用打包器、不用服务器，全部内联，双击即可打开，邮件传来传去也不会坏。任何人打开它就能运行。

为非开发人员而写。每个标签都使用**领域语言**，而不是代码：按钮和状态读起来要像业务语言，而不是 reducer。用平实的语言解释正在发生什么。

按清晰的层级自上而下排布：

1. **标题与一句话说明**，讲清这份演示可以探索什么（即第 1 步提出的问题）。
2. **当前状态**：完整的相关状态，渲染成易读的面板（带标签的字段，而不是原始 JSON 转储），每次点击后重新渲染，让变化可见。在有助于非开发人员理解的地方，点明刚刚发生了什么变化。
3. **自由操作按钮**：每个动作一个按钮，始终可用，任何人都能按任意顺序摆弄模型。每次点击派发对应的动作并重新渲染状态。
4. **引导式走查**：一组**场景**，每个场景一个标签页。每个标签页包含一段简短的平实语言场景描述（设定了什么情境、需要留意什么），其下方是该场景下按顺序**要点击的按钮**。每一步都是真实按钮：点击它就执行该动作并进入下一步。开始一次走查会重置到已知的初始状态，保证场景每次都以相同方式运行。

选择那些能演示棘手情况的场景，也就是纸面上难以推想清楚的情况：主路径、一个棘手的边界情况、一次本应不合法的尝试。

保持美观但克制：干净的排版、充裕的留白、一种强调色。不加动画，不玩噱头：任何东西都不能与状态和按钮争夺注意力。

### 4. 交付出去

把文件发给他们，或者替他们打开。他们会在有空时点击走查和自由操作；有意思的时刻是他们说「等等，这不该是可能的」或「咦，我以为 X 会不一样」的时候；那些是**想法**里的 bug，而这正是全部意义所在。如果他们想要新动作或新场景，就加上去。原型是会演进的。

### 5. 沉淀答案与原型

原型回答完问题之后，先沉淀答案，再按 [SKILL](SKILL.md) 所述的方式沉淀原型。逻辑层面的对应关系：经过验证的 reducer / 状态机 / 函数集提升到真实模块中（决策被吸收）；HTML 外壳随一次性分支保留，使原型作为一手资料留存；由于它是一个自包含的文件，在那里依然可以轻松重新运行。

## 反模式

- **不要加测试。** 需要测试的原型就不再是原型了。
- **不要接到真实数据库上。** 除非问题明确关乎持久化，否则使用内存状态。
- **不要泛化。** 不要做「万一以后想支持 X 怎么办」。原型只回答一个问题。
- **不要把逻辑和页面混在一起。** 如果纯模块引用了 DOM、`document` 或按钮处理器，它就无法被整体抽离。让页面保持为纯模块之上的薄外壳。
- **不要动用框架、打包器或服务器。** 收件人双击即可打开的单文件；一个 React 应用或开发服务器都会破坏「可分享」这一点。
- **不要把 HTML 外壳发到生产环境。** 页面是为手工点击走查而优化的。它背后的逻辑模块才是值得保留的部分。
