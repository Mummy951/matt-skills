# UI 原型

在同一路由上生成**若干差异极大的 UI 变体**，通过底部浮动栏切换。用户在浏览器中在各变体之间翻看，选定一个（或从每个变体中各取一部分），其余弃用。

如果问题关乎逻辑/状态，而非外观，这条分支就不对路。使用 [LOGIC.md](LOGIC.md)。

## 何时适用此形态

- 「这个页面应该长什么样？」
- 「在动手之前，我想先看看这个仪表盘的几个方案。」
- 「给设置界面换一种布局试试。」
- 每当用户本来要花一天时间在脑子里三个模糊的草稿之间纠结。

## 两个子形态：强烈优先子形态 A

当 UI 原型**嵌入应用其余部分**时，要好判断得多：真实的页头、真实的侧边栏、真实的数据、真实的信息密度。一个孤立存在的临时路由是真空环境：每个变体单独看都不错。只要存在一个可以承载各变体的现成页面，默认就采用子形态 A。只有当原型确实没有就近的归属时，才用子形态 B。

### 子形态 A：在现有页面上调整（首选）

路由已经存在。各变体**在同一路由上**渲染，由 `?variant=` URL 查询参数控制。现有的数据获取、参数和鉴权全部保留，只替换渲染部分。这是默认方案；除非有明确理由不选它，否则就选它。

如果原型对应的东西还没有页面，但*天然就该属于某个页面内部*（仪表盘的一个新分区、设置界面上的一张新卡片、现有流程中的一个新步骤），那仍属于子形态 A。把各变体挂载到宿主页面内部。

### 子形态 B：新建页面（最后手段）

只有当被原型化的东西确实没有现成页面可以容纳时才用（例如一个全新的顶层界面，或一个无法合理嵌入任何位置的流程）。

遵循项目已有的路由约定创建一条**临时路由**。不要发明新的顶层结构。命名要让人一眼看出它是原型（例如在路径或文件名中包含 `prototype` 一词）。沿用相同的 `?variant=` 模式。

在采用子形态 B 之前，先做一次合理性核查：真的没有可以嵌入的现成页面吗？一条空路由会掩盖设计问题，而有内容的路由会把它们暴露出来。

两种子形态中，底部浮动栏完全相同。

## 流程

### 1. 明确问题并选定 N

默认 **3 个变体**。超过 5 个就不再是差异，而开始变成噪声，所以上限设为 5。

把计划写在一行，放在原型所在位置或文件顶部注释里：

> 「设置页面的三个变体，通过 `?variant=` 切换，挂在现有 `/settings` 路由上。」

无论用户是来推进还是来反对，这一步都适用。

### 2. 生成差异显著的变体

起草每个变体。对每个变体守住：

- 页面的用途以及它可访问的数据。
- 项目的组件库 / 样式体系（TailwindCSS、shadcn、MUI、普通 CSS，等均可）。
- 一个清晰的导出组件名，例如 `VariantA`、`VariantB`、`VariantC`。

变体必须**在结构上不同**：不同的布局、不同的信息层级、不同的主要操作入口，而不只是颜色不同。三张微调过的卡片网格算不上 UI 原型，只是墙纸。如果两份草稿出来过于相似，就带着「不要用卡片网格」的明确指示重做其中一份。

### 3. 把它们接起来

在路由上创建一个单一的切换组件：

```tsx
// pseudo-code, adapt to the project's framework
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

对于子形态 A（现有页面）：在切换组件之上保留所有现有的数据获取；只有渲染子树随变体变化。

对于子形态 B（新页面）：`/prototype/<name>` 下的临时路由挂载同一个切换组件。

### 4. 构建浮动切换器

一个位于屏幕底部居中的小固定定位栏，包含三部分：

- **左箭头**：切换到上一个变体（循环环绕）。
- **变体标签**：显示当前变体的键；若变体导出了名称，也一并显示。例如 `B (Sidebar layout)`。
- **右箭头**：向前切换（循环环绕）。

行为：

- 点击箭头会更新 URL 查询参数（使用框架的路由，例如 Next 上的 `router.replace`、React Router 上的 `navigate` 等），这样变体可分享、刷新后保持稳定。
- 键盘：`←` 和 `→` 方向键同样循环切换。当 `<input>`、`<textarea>` 或 `[contenteditable]` 处于聚焦状态时，不要拦截方向键。
- 视觉上与页面明显区分（例如高对比胶囊、轻微阴影），让人一眼看出它不属于正在评估的设计。
- 在生产构建中隐藏：用 `process.env.NODE_ENV !== 'production'` 或等价检查做闸门，避免误并入的原型把这个栏带给用户。

把切换器做成一个共享组件，两种子形态都能复用。放在项目中存放共享 UI 的地方。

### 5. 交付

给出 URL（以及 `?variant=` 的各个键）。用户有空时会翻看。有意思的反馈通常是**「我想要 B 的页头加上 C 的侧边栏」**，那才是他们真正想要的设计。

### 6. 记录结论并清理

一旦某个变体胜出，记录结论（哪个变体以及原因），然后按 [SKILL](SKILL.md) 所述的方式留存原型。把胜出者并入真实代码，其余内容放到临时分支，而不是 main：

- **子形态 A**：把胜出者并入现有页面；从 main 中移除落败变体和切换器。
- **子形态 B**：把胜出变体提升为真实路由；从 main 中移除临时路由和切换器。

完整的变体集合是一手资料，因此应落到临时分支，而不是扔进垃圾箱；因为留在 main 分支里的变体组件和切换器会很快腐化，并让下一个阅读者困惑。

## 反模式

- **变体只在颜色或文案上有差别。** 那是微调，不是原型。真正的变体在结构上就有分歧。
- **变体之间共享过多代码。** 共享一个 `<Header>` 没问题；共享一个 `<Layout>` 就失去了意义。每个变体都应该可以自由抛弃布局。
- **把变体接到真实的变更操作上。** 只读的原型没问题。如果变体需要做变更，把它指向一个桩：问题是「这个应该长什么样」，而不是「后端能不能跑通」。
- **直接把原型提升到生产环境。** 变体代码是在原型约束下写的（没有测试、错误处理最少）。并入时要重新把它写规范。
