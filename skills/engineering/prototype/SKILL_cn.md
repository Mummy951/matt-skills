# 原型

原型是**用于回答某个问题的一次性代码**。问题决定原型的形态。

## 选择分支

借助用户的提示、周边代码来判断当前要回答的是哪个问题；如果用户就在旁边，也可以直接询问：

- **「这个逻辑 / 状态模型是否合理？」** → [LOGIC.md](LOGIC.md)。构建一个可分享的单 HTML 文件（自由操作按钮加上标签页式的引导演示），把状态机推入那些在纸面上难以推演的场景，并且非开发者也能操作。
- **「这个应该长什么样？」** → [UI.md](UI.md)。在同一条路由上生成几个截然不同的 UI 变体，通过 URL 查询参数和一个悬浮底部栏进行切换。

这两个分支产出的成品差异很大，选错方向会浪费整个原型。如果问题确实含糊不清，又联系不上用户，则默认选择与周边代码更匹配的分支（后端模块 → 逻辑；页面或组件 → UI），并在原型顶部写明这一假设。

## 两条分支共同适用的规则

1. **从第一天起就是一次性的，并明确标注如此。** 把原型代码放在它实际使用位置的附近（紧邻其为之做原型的模块或页面），让上下文一目了然；但命名要让随意翻阅的人一眼看出这是原型，而非生产代码。对于一次性的 UI 路由，遵循项目已有的路由约定，不要另起一套新的顶层结构。
2. **运行极为简单。** UI 原型通过项目任务运行器中的一条命令启动：`pnpm <name>`、`python <path>`、`bun <path>` 等。逻辑演示则是用户双击即可打开的单个 HTML 文件。无论哪种方式，启动都不需要任何思考。
3. **默认不做持久化。** 状态存放在内存中。持久化正是原型所要_检验_的对象，而不是它应当依赖的东西。如果问题明确涉及数据库，就使用一个临时数据库或本地文件，并起一个醒目的「PROTOTYPE, wipe me」名称。
4. **省略打磨。** 不写测试，不做除让原型_可运行_之外的错误处理，不做抽象。目的是快速学到东西。
5. **暴露状态。** 每次操作之后（逻辑）或每次切换变体时（UI），打印或渲染出完整的相关状态，让用户看到发生了什么变化。
6. **完成后留存。** 把任何已验证的决策并入真实代码，然后将原型本身作为**一手资料**留存：提交到一条一次性分支上，不进入 main，并在实现该 issue 上留下指向该分支的上下文线索。答案（结论及其所解答的问题）也一并记录在该 issue 或一次提交中。主分支只保留已验证的决策。
