# 代码库设计

设计**深度模块**：在一个小巧的接口之后隐藏大量行为，置于一处干净的接缝上，并可通过该接口进行测试。凡是在设计或重构代码的地方，都使用这套语言和这些原则。目标是为调用者提供杠杆效应，为维护者提供局部性，并让所有人都能测试。

## 术语表

请严格使用这些术语：不要用 "component"、"service"、"API" 或 "boundary" 来替代。语言一致正是全部意义所在。

**模块（Module）**：任何同时具有接口和实现的东西。刻意不绑定规模：可以是一个函数、一个类、一个包，或跨分层的一片切片。_避免使用_：unit、component、service。

**接口（Interface）**：调用者要正确使用该模块所必须了解的一切：既有类型签名，也包括不变量、顺序约束、错误模式、所需配置和性能特征。_避免使用_：API、signature（过于狭窄，它们仅指类型层面的表面）。

**实现（Implementation）**：模块内部的内容，即其代码主体。它与**适配器（Adapter）**不同：一个东西可以是小适配器配大实现（如 Postgres 仓库），也可以是大适配器配小实现（如内存版赝品）。当接缝是讨论主题时用 "adapter"；其余情况用 "implementation"。

**深度（Depth）**：接口处的杠杆效应。指调用者（或测试）每学习一单位接口所能调用到的行为量。当大量行为藏在一个小巧接口之后时，模块是**深的（deep）**；当接口几乎与实现同样复杂时，则是**浅的（shallow）**。

**接缝（Seam）** _(Michael Feathers)_：一个你无需在该处编辑即可改变行为的位置；模块接口所栖居的*位置*。接缝放在哪里，本身就是一项设计决策，与接缝背后放什么是两回事。_避免使用_：boundary（与 DDD 的限界上下文一词重载）。

**适配器（Adapter）**：在某个接缝处满足接口的具体事物。描述的是*角色*（它填补哪个槽位），而非实质内容（里面是什么）。

**杠杆效应（Leverage）**：调用者从深度中获得的东西。每学习一单位接口所获得的更多能力。一份实现可在 N 个调用点和 M 个测试中得到回报。

**局部性（Locality）**：维护者从深度中获得的东西。变更、缺陷、知识和验证都集中在一处，而不是散落到各个调用者中。修复一次，处处生效。

## 深模块与浅模块

**深模块（Deep module）** = 小接口 + 大量实现：

```
┌─────────────────────┐
│   Small Interface   │  ← Few methods, simple params
├─────────────────────┤
│                     │
│  Deep Implementation│  ← Complex logic hidden
│                     │
└─────────────────────┘
```

**浅模块（Shallow module）** = 大接口 + 少量实现（应避免）：

```
┌─────────────────────────────────┐
│       Large Interface           │  ← Many methods, complex params
├─────────────────────────────────┤
│  Thin Implementation            │  ← Just passes through
└─────────────────────────────────┘
```

设计接口时，追问自己：

- 我能否减少方法数量？
- 我能否简化参数？
- 我能否把更多复杂性藏到内部？

## 原则

- **深度是接口的属性，而非实现的属性。** 一个深度模块内部可以由小的、可 mock 的、可替换的部分组成；只是这些部分不属于接口。模块既可以有**内部接缝**（对其实现私有，供自身测试使用），也可以在其接口处有**外部接缝**。
- **删除测试。** 设想把该模块删掉。如果复杂性随之消失，那它只是个透传层。如果复杂性在 N 个调用方那里重新冒出来，说明它在物有所值地工作。
- **接口就是测试面。** 调用者和测试穿过同一道接缝。如果你想在接口*之外*再往下测试，这个模块的形态很可能就不对。
- **一个适配器意味着一道假想的接缝；两个适配器才意味着一道真实的接缝。** 除非确实有事物跨接缝产生差异，否则不要引入接缝。

## 为可测试性而设计

好的接口让测试变得自然：

1. **接收依赖，不要创建依赖。**

   ```typescript
   // Testable
   function processOrder(order, paymentGateway) {}

   // Hard to test
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **返回结果，不要产生副作用。**

   ```typescript
   // Testable
   function calculateDiscount(cart): Discount {}

   // Hard to test
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **小表面面积。** 方法越少，需要的测试越少。参数越少，测试搭建越简单。

## 关系

- 一个**模块**恰好拥有一个**接口**（它呈现给调用者和测试的表面）。
- **深度**是**模块**的属性，对照其**接口**来衡量。
- **接缝**是模块的**接口**栖居之处。
- **适配器**位于某道**接缝**上并满足该**接口**。
- **深度**为调用者产生**杠杆效应**，为维护者产生**局部性**。

## 已否决的提法

- **把深度当作实现行数与接口行数之比**（Ousterhout）：这种做法奖励给实现堆砌篇幅。我们改用「深度即杠杆效应」。
- **把 "Interface" 当作 TypeScript 的 `interface` 关键字或某个类的公共方法**：过于狭窄；此处的接口涵盖调用者必须了解的每一项事实。
- **"Boundary"**：与 DDD 的限界上下文一词重载。请说**接缝（seam）**或**接口（interface）**。
