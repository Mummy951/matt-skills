# 深化

如何在给定依赖关系的前提下，安全地深化一组浅层模块。本文沿用 [SKILL.md](SKILL.md) 中的词汇：**模块**、**接口**、**接缝**、**适配器**。

## 依赖分类

在评估一个候选深化对象时，先对其依赖进行分类。分类决定了深化后的模块如何跨接缝进行测试。

### 1. 进程内

纯计算、内存状态、无 I/O。始终可以深化：合并这些模块，直接通过新接口测试，无需适配器。

### 2. 本地可替代

拥有本地测试替身的依赖（Postgres 用 PGLite、内存文件系统）。若替身存在，则可深化。深化后的模块在测试套件中以替身运行来测试。接缝是内部的；模块外部接口上不设端口。

### 3. 远程但自有（端口与适配器）

跨网络边界的自有服务（微服务、内部 API）。在接缝处定义一个**端口**（接口）。深层模块拥有业务逻辑；传输层作为**适配器**被注入。测试使用内存适配器，生产环境使用 HTTP/gRPC/队列适配器。

建议表述：*"在接缝处定义一个端口，为生产环境实现一个 HTTP 适配器，为测试实现一个内存适配器；这样即使逻辑跨网络部署，也仍集中在一个深层模块中。"*

### 4. 真正外部（Mock）

你无法控制的第三方服务（Stripe、Twilio 等）。深化后的模块将外部依赖作为注入的端口；测试提供一个 mock 适配器。

## 接缝纪律

- **一个适配器意味着假想的接缝，两个适配器才意味着真正的接缝。** 除非能证明至少需要两个适配器（通常是生产 + 测试），否则不要引入端口。单适配器接缝只是单纯的间接层。
- **内部接缝与外部接缝。** 深层模块既可以在其接口处拥有外部接缝，也可以拥有内部接缝（对自身实现私有，仅供自身测试使用）。不要仅仅因为测试用到了内部接缝，就把它暴露到接口上。

## 测试策略：替换，而非叠加

- 一旦深化后模块的接口层面有了测试，针对浅层模块的旧单元测试就失去了价值，应删除。
- 在深化后模块的接口层面编写新测试。**接口就是测试面**。
- 测试通过接口断言可观察的结果，而不是内部状态。
- 测试应当能够经受住内部重构，因为它们描述的是行为，而不是实现。如果实现一变，测试就必须跟着改，说明这个测试越过了接口在做测试。
