# 改善代码库架构

揭示架构上的摩擦点，并提出**深化机会**：把浅层模块重构为深层模块的重构。目标是可测试性与 AI 可导航性。

本命令结合项目的领域模型，并建立在一套共享的设计词汇之上：

- 调用 Skill 工具并传入 "codebase-design"，获取架构词汇（**模块**、**接口**、**深度**、**接缝**、**适配器**、**杠杆**、**局部性**）及其原则（删除测试、「接口即测试面」、「一个适配器 = 假想接缝，两个 = 真实接缝」）。在每条建议中严格使用这些术语，不要漂移到「组件」「服务」「API」或「边界」等说法。
- `GLOSSARY.md` 中的领域语言为良好的接缝命名；`docs/adr/` 中的 ADR 记录了本命令不应重新争论的决策。

## 流程

### 1. 探索

**先界定范围，再扫描：YAGNI。** 深化一个模块的回报在于让未来对它的改动更容易，因此要额外重视代码库中近期发生过变更的部分。先决定*去哪里*看，再动手看：

- 如果用户已经指明了方向（某个模块、某个子系统、某个痛点），直接采纳，跳过下面的推断。
- 否则，回溯一段足够长的提交历史（`git log --oneline`），找出代码库的热点——反复出现的文件与区域，让这些路径最先吸引你的注意。如果变更分散、没有明确热点，就扩大排查范围。

先阅读项目的领域术语表（`GLOSSARY.md`）以及你所触及区域内的任何 ADR。

然后派出一个拥有全新上下文窗口的子代理来遍历代码库。不要套用僵化的启发式规则；要有机地探索，并记录你在何处感受到摩擦：

- 理解某个概念时，哪里需要在许多小模块之间来回跳转？
- 哪些模块是**浅层**的，其接口几乎和实现一样复杂？
- 哪些纯函数仅仅为了可测试性而被抽取出来，但真正的 bug 藏在它们被调用的方式里（缺乏**局部性**）？
- 哪些紧耦合的模块在各自接缝处相互泄漏？
- 代码库的哪些部分未经测试，或难以通过当前接口进行测试？

对你怀疑是浅层的任何东西应用**删除测试**：删掉它之后，复杂度是被集中起来了，还是仅仅被挪了个位置？「是的，被集中起来了」才是你想要的信号。

### 2. 以 HTML 报告呈现候选方案

将一个自包含的 HTML 文件写入操作系统临时目录，确保不向仓库中落任何文件。从 `$TMPDIR` 解析临时目录，回退到 `/tmp`（Windows 上为 `%TEMP%`），写入 `<tmpdir>/architecture-review-<timestamp>.html`，使每次运行都生成一个新文件。为用户打开它（Linux 上 `xdg-open <path>`，macOS 上 `open <path>`，Windows 上 `start <path>`），并告知其绝对路径。

报告使用 **Tailwind via CDN** 进行布局与样式，在图形/流程/时序能可靠传达结构时，使用 **Mermaid via CDN** 绘制图表。将 Mermaid 与手工打造的 CSS/SVG 视觉效果混合使用：当关系呈图状（调用图、依赖、时序）时用 Mermaid；当你想要更具编辑感的呈现（质量图、剖面图、折叠动画）时，用手工编写的 div/SVG。每个候选方案都配一张**改造前/后可视化对比**。要尽量视觉化。

对每个候选方案，渲染一张卡片，包含：

- **文件**：涉及哪些文件/模块
- **问题**：当前架构为何造成摩擦
- **方案**：用平实的英文描述将会改变什么
- **收益**：从局部性与杠杆的角度解释，以及测试将如何改善
- **改造前 / 后图**：并排呈现，手工绘制，展示浅层状态与深化后的状态
- **推荐强度**：`Strong`、`Worth exploring`、`Speculative` 之一，渲染为徽标

报告结尾设置一个**首选推荐**章节：你会先处理哪个候选方案，以及原因。

**领域词汇使用 `GLOSSARY.md` 中的说法，架构词汇使用 `/codebase-design` 中的说法。** 如果 `GLOSSARY.md` 定义了 "Order"，就谈论「Order 接入模块」，而不是 "FooBarHandler"，也不是 "Order 服务"。

**ADR 冲突**：如果某个候选方案与现有 ADR 相抵触，只有当摩擦确实严重到值得重新审视该 ADR 时才将其提出。在卡片中明确标注（例如一个警示提示框：_"contradicts ADR-0007, but worth reopening because…"_）。不要把 ADR 禁止的每一种理论上的重构都列出来。

完整的 HTML 脚手架、图表模式与样式指引见 [HTML-REPORT.md](HTML-REPORT.md)。

暂不要提出接口。文件写完后，询问用户："Which of these would you like to explore?"

### 3. 深入质询循环

用户选定一个候选方案后，调用 Skill 工具并传入 "grilling"，与他们一起走完决策树：约束、依赖、深化后模块的形态、接缝背后是什么、哪些测试得以保留。

随着决策逐渐成型，副作用就地发生；在推进过程中调用 Skill 工具并传入 "domain-modeling"，使领域模型保持最新：

- **为深化后的模块命名时使用了一个 `GLOSSARY.md` 中没有的概念？** 将该术语加入 `GLOSSARY.md`。若文件尚不存在，则按需创建。
- **在对话中细化了一个模糊术语？** 当场更新 `GLOSSARY.md`。
- **用户以一个承重性理由拒绝了该候选方案？** 提议记录一条 ADR，表述为：_"Want me to record this as an ADR so future architecture reviews don't re-suggest it?"_ 仅当该理由确实会被未来的探索者需要、以避免再次提出同样建议时才提议；跳过临时性理由（"not worth it right now"）和不言自明的理由。
- **想为深化后的模块探索备选接口？** 调用 Skill 工具并传入 "codebase-design"，使用其设计两遍的并行子代理模式。
