# Wizard

**wizard** 是一个 bash 脚本，一步步引导人类完成一项手工流程：手工操作繁琐，每次再向 AI 重新解释一遍同样繁琐。它会打开每个 URL，明确说明点击哪里、复制什么，捕获对应的值，写到该去的地方（`.env`、GitHub secrets），在每个阶段确认，并提示还剩多少个阶段。它可能用于配置第三方服务、执行一次性迁移，或将项目从一种状态推进到另一种状态。

友好的用户体验已由 [template.sh](template.sh) 解决：分阶段进度、确认关卡、跨平台打开 URL（含 WSL）、密钥隐藏输入、幂等的 `.env` upsert、`gh secret`/`gh variable` 写入，以及收尾总结。**你的工作只是界定流程范围并编写各个阶段。** `STAGES` 标记以上的库代码在每个 wizard 中都完全相同；这种一致性正是目的所在：切勿手工改动它。

wizard 默认是临时性的：为单次运行而建，存放在临时目录或 `scripts/` 路径下，任务完成后删除。只有当用户希望保留一条可重复的搭建路径并纳入仓库时，才将其提交。

## 流程

### 1. 界定流程范围

梳理出人类必须执行的每一个手工步骤，以及沿途捕获的每一个值。先阅读仓库，不要凭空发问：

- 搭建类：`.env`、`.env.example`、`.env.*`、`README`、`docker-compose*`、框架配置，以及 `.github/workflows/*`（每一处 `secrets.*` / `vars.*` 引用都是 wizard 必须产出的值）。
- 迁移或过渡类：当前状态、目标状态，以及两者之间不可逆的操作。

然后向用户展示按顺序排列的阶段清单及每个阶段产出的值，并确认：用户可能会增删或调整顺序。

**完成标准：** 每个阶段都按顺序命名；对于每个捕获的值，你都清楚（a）人类从哪里获取它，（b）写到哪里（`.env`、GitHub secret、两者都写，或不落盘；有些阶段只是纯操作），以及（c）它是否为密钥（隐藏输入）还是公开值。

### 2. 梳理每个阶段的路径

为每个阶段写出人类遵循的精确路径：打开哪个 URL、在那里做什么、值显示在哪里、填入哪个变量；例如「控制台 → Developers → API keys → Reveal test key → 复制」。在你并不真正了解当前界面或确切命令的地方，如实说明并向用户询问或查阅文档：绝不要编造可能并不存在的步骤。

**完成标准：** 每个阶段都能追溯到陌生人也能照做的具体指令。

### 3. 编写 wizard

将 `template.sh` 复制到目标路径。把示例阶段替换为每步一个 `stage`，按依赖顺序排列。使用库提供的辅助函数：`stage`、`say`/`step`、`open_url`、`ask`/`ask_secret`、`write_env`、`set_secret`/`set_var`、`pause`/`confirm`。将 `TOTAL_STAGES` 设为你编写的阶段数量。

保持模板所设定的标准：在索要某个值之前先打开对应 URL，凡是密钥都用 `ask_secret`，每个持久化的值都用 `write_env` 写入，`set_secret` 只用于 CI 真正需要的值，任何不可逆操作之前都要 `confirm`。每个 `stage` 会清屏，只显示当前步骤：让一个阶段只专注一项任务，避免人类需要的内容被滚出屏幕。不要触碰标记以上的库代码。

### 4. 验证并交付

- `bash -n <script>`；如有可用，运行 `shellcheck`。
- `chmod +x <script>`。
- 不要自己端到端运行它：它会打开浏览器并阻塞等待人工输入。改为静态走查：第 1 步产生的每个值都被捕获，并落到第 1 步所说的位置；每个 `set_secret` 名称都与 CI 中的 `secrets.*` 引用精确匹配。
- 告诉用户如何运行它。如果这是一条可重复的搭建路径，就提交它，并从 README 中链接过去，让下一个人运行脚本，而不是再去询问 AI。
