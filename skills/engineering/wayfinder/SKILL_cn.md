一个模糊的想法已经成形，规模超出单个智能体会话所能承载的范围，而且笼罩在迷雾之中：从此处通往**目标**的路径目前还不可见。寻路（wayfinding）的重点是找到那条路径，而不是直接冲向目标。本技能把这条路径绘制成仓库 issue 跟踪器上的一张**共享地图**，然后逐个处理其上的**决策工单**（其解决结果是一项决策，而非待执行的构建切片），直到路线清晰为止。

目标因工作而异，而命名目标是绘图的第一步：它决定每一张工单的形态。它可能是一份用于交接和迭代的规格、一个在规划开始前需要锁定的决策，或是一次原地进行的变更（例如数据结构迁移）。地图不局限于特定领域：工程工作、课程内容，任何符合这一形态的事项均可适用。

## 规划，而非执行

wayfinder 默认做的是**规划**：每张工单解决一项决策；当路径清晰、在有人着手实施之前已没有需要再决定的事项时，地图即告完成。那种想直接动手干活的冲动，通常是一个信号：你已经抵达地图的边缘，是时候交接了。某项工作可以在其 **Notes** 中覆盖这一设定，把执行本身纳入地图；若没有这样的覆盖，则产出决策，而不是交付物。

## 按名称引用

每张地图和每张工单都是一个 issue，因此都有一个**名称**：它的标题。在人会阅读的所有内容中（叙述文字、地图的「Decisions so far」），都按该名称引用它，绝不使用裸 id、编号或 slug。一长串 `#42, #43, #44` 难以辨认；名称则一目了然。id 和 URL 并不会消失：名称包裹着它的链接，二者位于名称**之内**，但绝不能取代名称。

## 地图

地图是本仓库 issue 跟踪器上的单个 issue，标签为 `wayfinder:map`，是规范的产物。它的工单都是地图的子 issue。

地图是**索引**，而不是存储库。它列出已作出的决策，并指向保存其细节的工单；一项决策只存在于唯一一处——它的工单，因此地图从不重述决策内容，只做概括并附上链接。

**地图、其子工单、阻塞关系以及前沿查询实际存放于何处，取决于具体的跟踪器。** issue 跟踪器应当已经提供给你。如果没有，请告知用户运行 `/setup-matt-pocock-skills`。关于**本**仓库如何表达这些内容，请查阅跟踪器文档的「Wayfinding operations」一节。若未提供任何跟踪器，则默认使用本地 markdown 跟踪器。

### 地图正文

整张地图的低分辨率概览，每个会话加载一次。未关闭的工单**不**在此列出：它们是开放的子 issue，通过查询找到。

```markdown
## Destination

<what reaching the end of this map looks like: the spec, decision, or change this effort is finding its way to. One or two lines; every session orients to it before choosing a ticket.>

## Notes

<domain; skills every session should consult; standing preferences for this effort>

## Decisions so far

<!-- the index: one line per closed ticket, enough to judge relevance, then zoom the link for the detail the ticket holds -->

- [<closed ticket title>](link): <one-line gist of the answer>

## Not yet specified

<!-- see "Fog of war": in-scope fog you can't ticket yet; graduates as the frontier advances -->

## Out of scope

<!-- see "Out of scope": work ruled beyond the destination; closed, never graduates -->
```

### 工单

每张工单都是地图的**子 issue**；跟踪器的 issue id 就是它的身份标识。工单正文即问题本身，规模控制在一个 100K token 的智能体会话可处理的范围内：

```markdown
## Question

<the decision or investigation this ticket resolves>
```

每张工单带有 `wayfinder:<type>` 标签，取值为 `research`、`prototype`、`grilling`、`task` 之一（参见 [Ticket Types](#ticket-types)）。`wayfinder:` 标签是地图及其工单唯一携带的标签，绝不使用 `ready-for-agent` 这类分诊标签：它们是决策，而不是实现工作。

会话通过把工单指派给驱动地图的开发者来**认领**工单，且必须在任何工作开始**之前**完成，以便并发会话跳过它。该指派人**就是**认领状态：开放且未指派的工单即尚未被认领。

阻塞关系使用跟踪器**原生**的依赖关系：这一点至关重要，因为它能在跟踪器自身的 UI 中**以可视化方式**呈现前沿，让人无需打开地图即可看到哪些工单可以接手。只有在跟踪器缺乏原生阻塞能力时，才回退到正文约定。当阻塞某工单的所有工单都已关闭时，该工单即为**已解除阻塞**；**前沿**就是开放、已解除阻塞、尚未被认领的子工单，即已知领域的边界。

答案不属于工单正文；它在解决时记录（参见 [Work through the map](#work-through-the-map)）。解决工单过程中创建的资产通过 issue 链接引用，而不是粘贴进正文。

## 工单类型

每张工单要么是 **HITL**（human in the loop，人在环中，与一位为自己发声的人**协作**完成），要么是 **AFK**，由智能体独立驱动。HITL 工单只能通过这种实时交流来解决；智能体绝不代替人这一方作答（一个自己回答自己问题的 grilling 智能体就违反了这一点）。

- **Research**（AFK）：阅读文档、第三方 API 或知识库等本地资源，揭示某项决策所等待的事实。由一个子代理调用 Skill 工具并指定 "research" 来解决。当需要当前工作目录之外的知识时使用。
- **Prototype**（HITL）：通过调用 Skill 工具并指定 "prototype"，制作一个廉价、粗略但具体的产物（提纲、粗略方案、桩代码或 UI/逻辑代码）供讨论反馈，从而提升讨论的保真度。原型作为资产附上链接。当「它应该长什么样」或「它应该如何运作」是核心问题时使用。
- **Grilling**（HITL）：对话。默认情形。始终调用 Skill 工具两次，分别指定 "grilling" 和 "domain-modeling"。
- **Task**（HITL 或 AFK）：在作出**决策**之前必须完成的手动工作：其中没有需要决策、原型制作或调研的内容，但讨论在其完成前一直处于阻塞状态。例如注册某项服务以便评判其 API、开通访问权限、迁移数据以便查看其形态。这是唯一一类**执行**而非决策的工单，其存在价值在于解除某项决策的阻塞，而不是交付目标。智能体能独立完成时即独立驱动（AFK）；否则向人提供一份精确的清单（HITL）。工作完成后即视为解决；答案记录所做的工作，以及后续工单所依赖的任何由此产生的事实（凭证位置、新 URL、行数等）。

## 战争迷雾

地图**有意**保持不完整：不要把你尚不可见的内容绘入图中。在现行工单之外是**战争迷雾**：对那些你能判断即将到来、但尚无法确定的决策与调研的模糊认知，因为它们取决于仍悬而未决的问题。解决一张工单会清除其前方的迷雾，把目前已可明确表述的内容逐步毕业为新的工单，一次一张，直到通往目标的路径清晰、不再有遗留工单。

地图的 **Not yet specified** 一节用于记录这种模糊认知：疑似的问题、日后需要重访的领域。它是**朝向**目标方向尚未探明的前沿：此处的一切都在范围内，只是还不够清晰，无法形成工单。可按认知的清晰程度，写得简略或详尽；它同时也充当路牌，帮助协作者了解这项工作的走向。

**迷雾还是工单？** 判断标准是你现在能否精确表述该问题，**而不是**你现在能否回答它。

- **形成工单的情形**：问题已经清晰，即使它处于阻塞状态、你暂时还无法着手处理。
- **归入 Not yet specified 的情形**：你尚无法如此清晰地表述它。不要预先把迷雾切成工单大小的小块：迷雾比工单更粗粒度；当前沿抵达某一块迷雾时，它可能毕业为若干工单，也可能一张都不毕业。

**Not yet specified** 不包含已作出决策的内容（Decisions so far）、已是现行工单的内容，以及超出范围的内容（下一节）。

## 超出范围

迷雾只会**朝向**目标方向聚集。目标确定了范围，因此超出目标的工作即为**超出范围**：它不是迷雾，也不应归入 **Not yet specified**。它在地图上拥有独立的 **Out of scope** 一节：指你有意识地排除在**本**项工作之外的内容。让内容落入此处的是范围，而不是清晰度。

超出范围的工作永远不会毕业（前沿止步于目标），因此只有在目标被重新划定后才可能回归，且届时是作为一项全新工作，而不是恢复原有工作。

将某项内容判定为超出范围是一次划定范围的行为，而不是路线上的一个步骤。当一张已存在的工单被发现位于目标之外（绘图时误纳入范围，或在某次解决中暴露出来），**关闭它**（已关闭的工单无疑位于前沿之外），并在 **Out of scope** 一节留下一行：概括其内容，并说明它为何超出范围，同时附上该已关闭工单的链接。它不进入 **Decisions so far**——后者记录实际走过的路线；范围边界不是路线上的步骤。

## 调用方式

两种模式。无论哪种模式，**每个会话绝不解决超过一张工单**，research 工单除外。

### 绘制地图

用户带着一个模糊的想法发起调用。

1. **命名目标。** 调用 Skill 工具两次，分别指定 "grilling" 和 "domain-modeling"，以确定这张地图要通往什么：规格、决策或变更。目标确定范围，因此首先敲定。
2. **勾勒前沿。** 再次进行深入质询，这次采用**广度优先**：在整个空间中铺开，而不是深入任何单一线索，揭示悬而未决的决策以及现在即可采取的最初步骤。**如果这一过程没有浮现出任何迷雾**（通往目标的路径已经清晰，整段旅程小到足以由一个会话完成），则不需要地图。停止并询问用户希望如何继续。
3. **创建地图**（标签 `wayfinder:map`）：填入 Destination 和 Notes，Decisions-so-far 留空，把迷雾勾勒进 **Not yet specified**。
4. **创建目前已可明确表述的工单**，作为地图的子 issue，然后在**第二轮**中连接阻塞关系（issue 需要先有 id，才能相互引用）。交叉引用也在这一轮写入，并使用真实 id：占位符 `#<n>` 会自动链接到一个无关的 issue。连接完成后，工单被归入前沿或阻塞两类；所有尚无法明确表述的内容留在迷雾中，即 **Not yet specified** 一节。
5. **启动调研子代理。** 为刚创建的每张 `research` 工单，启动一个拥有全新上下文窗口的子代理，调用 Skill 工具并指定 "research" 并行解决，将其发现记录在一条一次性的 `research/<name>` 分支上，并从工单给出上下文指针。推送该分支，但不要创建 PR：它永远不会被合并。
6. 停止：绘图是一个会话的工作；它不亲手解决任何工单。

### 推进地图

用户带着一张地图（URL 或编号）发起调用。工单是**可选的**：若未指定工单，则由你来选择下一项决策，而不是由用户选择。

1. 加载**地图**：低分辨率概览，而不是每张工单的正文。
2. 选择工单。若用户指定了某张，就使用它；否则按顺序取第一张前沿工单。**认领它**：在任何工作开始前将其指派给自己。
3. 按其 `wayfinder:<type>` 标签所指明的类型解决它（参见 [Ticket Types](#ticket-types)）。读取标签，而不只是正文：正文从不说明类型。**按需缩放查看**：按需获取任何相关或已关闭工单的完整正文；为 `## Notes` 块中列出的各项技能调用 Skill 工具。如有疑问，调用 Skill 工具两次，分别指定 "grilling" 和 "domain-modeling"。
4. 记录解决结果：将答案作为**解决评论**发布，**关闭**该 issue，并向地图的 Decisions-so-far **追加一条上下文指针**。
5. 添加新浮现出的工单（先创建再连接）；把答案使其变为可明确表述的迷雾毕业为工单，将每一块毕业的迷雾从 **Not yet specified** 中清除，使其仅以新工单的形式存在。如果答案揭示某张工单（本张或其他工单）位于目标之外，应**将其判定为超出范围**，而不是在路线上解决它。如果该决策使地图的其他部分失效，则更新或删除那些工单。

用户可能并行推进已解除阻塞的工单，因此要预期其他会话正在并发编辑跟踪器。
