对 `HEAD` 与用户给定的固定点之间的差异进行双维度评审：

- **Standards（标准）**：代码是否符合本仓库文档化的编码标准？
- **Spec（规格）**：代码是否忠实地实现了原始 issue / 规格？

两条维度各自作为**并行子代理**运行，避免互相污染上下文，随后由本技能汇总两者的发现。每个子代理都要以全新的上下文窗口启动。

issue 跟踪器应当已经提供给你。若没有，请告知用户运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 锁定固定点

以用户所说的内容作为固定点（提交 SHA、分支名、标签、`main`、`HEAD~5` 等）。若用户未指定，请向其询问。

一次性记录差异命令：`git diff <fixed-point>...HEAD`（三个点，因此比较的是相对于 merge-base 的差异）。同时通过 `git log <fixed-point>..HEAD --oneline` 记录提交列表。

继续之前，确认固定点可以解析（`git rev-parse <fixed-point>`）且差异非空。错误的 ref 或空差异应当在这里就失败，而不是留到两个并行子代理内部才暴露。

### 2. 识别规格来源

按以下顺序查找原始规格：

1. 提交信息中的 issue 引用（`#123`、`Closes #45`、GitLab `!67` 等），通过跟踪器文档中的工作流获取。
2. 用户作为参数传入的路径。
3. `docs/`、`specs/` 或 `.scratch/` 下与分支名或功能相匹配的规格文件。
4. 若一无所获，向用户询问规格在哪里。若用户表示没有规格，**Spec** 子代理将跳过并汇报「无可用规格」。

### 3. 识别标准来源

在仓库中搜索所有记录代码编写规范的文件。若存在 `CODING_STANDARDS.md` 或 `CONTRIBUTING.md`，必须列入清单。

除仓库中已记录的内容外，标准维度还始终携带以下**坏味道基线**：一套固定的 Fowler 代码坏味道（_Refactoring_ 第 3 章），即使仓库没有任何文档也适用。它受两条规则约束：

- **仓库标准优先。** 已记录的仓库标准始终优先；若仓库标准认可了某样基线本会标记的内容，则压下该坏味道。
- **始终是判断性结论。** 每个坏味道都是一条带标签的启发式规则（「可能的 Feature Envy」），绝不是硬性违规。与此处的其他标准一样，工具链已经强制约束的内容可跳过。

每条坏味道按 *它是什么* → *如何修复* 的方式描述，对照差异进行匹配：

- **Mysterious Name（神秘命名）**：一个函数、变量或类型，其名字未能揭示它做什么或持有什么。→ 重命名；若想不出一个诚实贴切的名字，说明设计本身含混不清。
- **Duplicated Code（重复代码）**：相同的逻辑结构在变更中的多个代码片段或文件里重复出现。→ 提取出共享结构，在两处调用它。
- **Feature Envy（依恋情结）**：一个方法更多地访问另一个对象的数据，而非自身的数据。→ 将该方法移动到它所依恋的数据所在之处。
- **Data Clumps（数据泥团）**：相同的几个字段或参数总是结伴出现（一个即将诞生的类型）。→ 将它们捆绑为一个类型，传递该类型。
- **Primitive Obsession（基本类型偏执）**：用基本类型或字符串代替了一个理应拥有自己类型的领域概念。→ 为该概念定义一个小类型。
- **Repeated Switches（重复的 switch）**：针对同一类型的相同 `switch`/`if` 级联在变更中反复出现。→ 用多态替换，或用一处两处共享的映射表替换。
- **Shotgun Surgery（霰弹式修改）**：一次逻辑变更迫使在差异中的许多文件里做零散修改。→ 把总是一起变化的内容聚合到一个模块中。
- **Divergent Change（发散式变化）**：同一个文件或模块因若干互不相关的原因被修改。→ 拆分，使每个模块只因一个原因而变化。
- **Speculative Generality（投机泛化）**：为规格中并不存在的需求添加抽象、参数或钩子。→ 删除它；内联回去，直到出现真实需求。
- **Message Chains（消息链）**：过长的 `a.b().c().d()` 导航链，调用方不应依赖它。→ 将这段遍历隐藏在首个对象的一个方法之后。
- **Middle Man（中间人）**：一个类或函数大多只是转发调用。→ 砍掉它，直接调用真正的目标。
- **Refused Bequest（被拒绝的遗赠）**：子类或实现者忽略或覆盖了继承而来的大部分内容。→ 放弃继承，改用组合。

### 4. 并行启动两个子代理

同时发出两个子代理调用（前台执行），并汇总它们返回的报告。

**Standards 子代理提示词**应包含：

- 完整的差异命令与提交列表。
- 第 3 步中找到的标准来源文件清单，**外加完整粘贴第 3 步的坏味道基线**（子代理没有其他途径获取它）。
- 简报："按文件/代码片段（在相关时）汇报：(a) 差异中违反已记录标准的每一处：引用对应标准（文件 + 规则）；(b) 你发现的任何基线坏味道：给出名称并引用该片段。区分硬性违规与判断性结论：违反已记录标准可以是硬性违规，但基线坏味道始终是判断性结论，且已记录的仓库标准优先于基线。跳过工具链已强制约束的内容。400 词以内。"

**Spec 子代理提示词**应包含：

- 差异命令与提交列表。
- 规格的路径或获取到的内容。
- 简报："汇报：(a) 规格要求但缺失或只实现了一部分的需求；(b) 差异中未被要求的行为（范围蔓延）；(c) 看似已实现但实现方式看起来有误的需求。每条发现都引用规格中的对应行。400 词以内。"

若规格缺失，跳过 Spec 子代理，并在最终报告中注明这一点。

### 5. 汇总

将两份报告分别置于 `## Standards` 和 `## Spec` 标题之下，原文照搬或轻度清理。**不要**合并或重新排序发现项，因为两条维度是刻意分开的（见 _Why two axes_）。

结尾用一行总结：每条维度的发现总数，以及_该维度内_最严重的 issue（如有）。不要跨维度选出唯一的优胜者：这种重排正是维度分离所要防止的。

## 为什么分为两条维度

一次变更可能通过一条维度、却未通过另一条：

- 代码遵循了每一项标准，却实现了错误的内容 → **Standards 通过，Spec 未通过。**
- 代码完全按 issue 的要求实现，却破坏了项目惯例 → **Spec 通过，Standards 未通过。**

分开汇报可以防止一条维度掩盖另一条维度的问题。
