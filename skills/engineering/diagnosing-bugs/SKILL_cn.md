# 诊断 Bug

一套应对疑难 bug 的纪律。只有在明确说明理由时，才可跳过某个阶段。

探索代码库时，先阅读 `GLOSSARY.md`（如果存在），以获得对相关模块清晰的心智模型，并查看你所涉及区域的 ADR。

## 脱敏

本技能要求你展示命令、输出和采集到的产物。**先脱敏每一处机密**：在其位置写上 `<REDACTED>`。针对环境变量构建循环，使凭证留在环境中，而不是出现在你展示的内容里。采集到的产物会携带认证头：只引用携带信号的那些行。

如果脱敏后的输出不足以诊断该 bug，明确说明并向用户询问。

## 阶段 1：构建反馈循环

**这就是本技能的核心。** 其余一切都是机械性工作。如果你对这个 bug 有一个**紧凑**的通过/失败信号（一个在_这个_ bug 上会变红的信号），你就能找到根因；二分定位、假设检验、插桩都只是在消耗这个信号。如果没有信号，再怎么盯着代码看也救不了你。

在这里投入不成比例的精力。**要激进。要有创意。拒绝放弃。**

### 构建循环的方式（大致按此顺序）

1. 在能触及该 bug 的任意接缝处编写**失败的测试**：单元、集成、e2e。
2. 针对运行中的开发服务器编写 **curl / HTTP 脚本**。
3. 用 fixture 输入进行 **CLI 调用**，将 stdout 与一份已知正确的快照做差异比对。
4. **无头浏览器脚本**（Playwright / Puppeteer），驱动 UI 并对 DOM/控制台/网络做断言。
5. **重放一段采集到的 trace。** 把真实的网络请求 / 载荷 / 事件日志保存到磁盘；在隔离状态下通过代码路径重放它。
6. **一次性临时 harness。** 启动系统的最小子集（一个服务、mock 掉依赖），用一次函数调用就触发该 bug 代码路径。
7. **属性 / fuzz 循环。** 如果 bug 是「偶尔输出错误」，跑 1000 个随机输入，寻找失败模式。
8. **二分定位 harness。** 如果 bug 出现在两个已知状态（提交、数据集、版本）之间，把「在状态 X 启动、检查、重复」自动化，以便用 `git bisect run` 跑它。
9. **差异对照循环。** 用同一输入分别跑旧版本与新版本（或两份配置），比对输出差异。
10. **HITL bash 脚本。** 最后手段。如果必须有人工点击，就用 `scripts/hitl-loop.template.sh` 驱动_这个人_，使循环仍然是结构化的。采集到的输出再反馈给你。

构建出正确的反馈循环，bug 就已经修复了 90%。

### 收紧循环

把循环当成一个产品来打磨。一旦有了_一个_循环，就**收紧**它：

- 我能让它更快吗？（缓存初始化、跳过无关初始化、收窄测试范围。）
- 我能让信号更锐利吗？（针对具体症状做断言，而不是「没崩溃」。）
- 我能让它更确定吗？（固定时间、给随机数设定种子、隔离文件系统、冻结网络。）

一个 30 秒、不稳定的循环，比没有循环好不了多少；一个 2 秒、确定性的循环则是一项调试超能力。

### 非确定性 bug

目标不是一份干净的复现，而是**更高的复现率**。把触发方式循环跑 100 次、并行化、加压、收窄时间窗口、注入 sleep。一个 50% 概率偶现的 bug 是可调试的；1% 则不行，所以要持续提高复现率，直到它可调试为止。

### 确实无法构建循环时

停下来，明确说明这一点。列出你已经尝试过的方法。向用户请求：(a) 访问任何能复现它的环境，(b) 一份脱敏后的采集产物（HAR 文件、日志转储、核心转储、带时间戳的屏幕录像），或 (c) 允许添加临时的生产环境插桩。**不要**在没有循环的情况下直接进入假设阶段。

### 完成标准：一个会变红的紧凑循环

阶段 1 完成的标志是：循环**紧凑**且**可变红**：你能说出**一条命令**（脚本路径、一次测试调用、一个 curl），并且你**已经至少运行过一次**（展示调用方式及其脱敏后的输出），该命令满足：

- [ ] **可变红**：它走真实的 bug 代码路径，并断言**用户所描述的确切症状**，因此能在这个 bug 上变红、修复后变绿。而不是「运行没报错」；它必须能够_抓住这个特定的 bug_。
- [ ] **确定性**：每次运行结论一致（不稳定的 bug：按上述方式固定住一个较高的复现率）。
- [ ] **快**：以秒计，而不是分钟计。
- [ ] **可由智能体运行**：你可以无人值守地跑它；人工介入只能通过 `scripts/hitl-loop.template.sh`。

如果你发现自己在这条命令存在之前就开始读代码、构建理论，**停下来：直接跳到假设正是本技能要避免的典型失败。** 没有可变红的命令，就不进入阶段 2。

## 阶段 2：复现 + 最小化

运行循环。看着它在 bug 出现时变红。

确认：

- [ ] 循环产生的是**用户**描述的失败模式，而不是恰好出现在附近的另一个失败。搞错 bug = 修复错方向。
- [ ] 该失败在多次运行中可复现（对于非确定性 bug，则以足够高的复现率可复现，足以据此调试）。
- [ ] 你已经采集到确切症状（错误信息、错误输出、缓慢的耗时），以便后续阶段验证修复确实解决了它。

### 最小化

一旦变红，把复现缩减到**仍然会变红的最小场景**。**一次一项**地砍掉输入、调用方、配置、数据和步骤，每次删减后重新运行循环，只保留对该失败起支撑作用的部分。

为什么要这么做：最小复现能缩小阶段 3 的假设空间（剩下需要怀疑的活动部件更少），并在阶段 5 成为干净的回归测试。

完成的标志是：**剩下的每个元素都是起支撑作用的**：去掉其中任何一个，循环都会变绿。

在复现**并**最小化之前，不要继续往下走。

## 阶段 3：提出假设

在测试任何假设之前，先生成 **3–5 个按优先级排序的假设**。只生成单一假设会锚定在第一个看似合理的想法上。

每个假设都必须**可证伪**：说清它做出的预测。

> 格式：「如果 <X> 是根因，那么 <改变 Y> 会让 bug 消失 / <改变 Z> 会让它更严重。」

如果你说不出预测，这个假设只是一种直觉：丢弃或把它打磨锐利。

**在测试之前，把排序后的清单展示给用户。** 他们往往具备领域知识，能立刻重新排序（「我们刚部署了对 #3 的一处改动」），或者知道哪些假设他们已经排除过。这是一个低成本的检查点，能节省大量时间。不要在此阻塞；如果用户不在，就按你自己的排序继续。

## 阶段 4：插桩

每一个探针都必须对应阶段 3 中的一条具体预测。**一次只改变一个变量。**

工具优先级：

1. 如果环境支持，优先用**调试器 / REPL 检查**。一个断点胜过十条日志。
2. 在能够区分各假设的边界处放置**有针对性的日志**。
3. 绝不「记录一切再去 grep」。

**给每条调试日志打上标签**，使用唯一前缀，例如 `[DEBUG-a4f2]`。最后清理时一次 grep 即可完成。没打标签的日志会留存下来；打了标签的日志会被清掉。

**性能分支。** 对于性能回退，日志通常是错的。应改为：先建立基线测量（计时 harness、`performance.now()`、剖析器、查询计划），然后二分定位。先测量，后修复。

## 阶段 5：修复 + 回归测试

在修复**之前**编写回归测试，但前提是存在一个**正确的接缝**来放它。

正确的接缝是指：测试能够在调用点真实发生的位置上，演练**真实的 bug 模式**。如果唯一可用的接缝过于浅（bug 需要多个调用方，却只有单调用方测试；单元测试无法复现触发 bug 的那条链路），在那里写回归测试只会带来虚假的信心。

**如果不存在正确的接缝，这本身就是一个结论。** 记录下来。代码库的架构正在阻碍这个 bug 被锁定。把这一点标记出来，留给下一阶段。

如果存在正确的接缝：

1. 把最小化后的复现改造成该接缝处的一个失败测试。
2. 看着它失败。如果你是通过改动代码或 fixture 强制变红的，先与一份原始副本做 `diff`，证明改动确实生效，再去信任它。
3. 应用修复。
4. 看着它通过。
5. 针对原始（未最小化）场景重新运行阶段 1 的反馈循环。

## 阶段 6：清理

宣布完成前必须完成：

- [ ] 原始复现不再出现（重新运行阶段 1 循环）
- [ ] 回归测试通过（或已记录无接缝的情况）
- [ ] 所有 `[DEBUG-...]` 插桩已移除（用前缀 `grep` 检查）
- [ ] 一次性原型已删除（或移到有明确标记的调试位置）
- [ ] 最终被证明正确的假设已写进提交 / PR 信息中，方便下一位调试者学习
