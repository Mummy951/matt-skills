# ADR 格式

ADR 存放在 `docs/adr/` 中，使用顺序编号：`0001-slug.md`、`0002-slug.md` 等。

按需创建 `docs/adr/` 目录：仅在需要第一份 ADR 时才创建。

## 模板

```md
# {Short title of the decision}

{1-3 sentences: what's the context, what did we decide, and why.}
```

仅此而已。一份 ADR 可以只有一个段落。其价值在于记录*做出了某个决策*以及*为什么*，而不在于填满各个章节。

## 可选章节

仅在确实有价值时才加入这些内容。大多数 ADR 并不需要。

- **Status** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）：在决策需要被重新审视时有用
- **Considered Options**：仅当被否决的备选方案值得被记住时才列出
- **Consequences**：仅当存在需要点明的、并不显而易见的下游影响时才列出

## 编号

扫描 `docs/adr/` 中已有的最大编号，并加一。

## 何时应提供 ADR

以下三条必须同时成立：

1. **难以逆转**：日后改变主意的成本很高
2. **脱离上下文会令人意外**：未来的读者看到代码时会纳闷「他们到底为什么这样做？」
3. **真实权衡的结果**：确实存在备选方案，而你基于具体理由选择了其中之一

如果一个决策容易逆转，就跳过它：你反正会把它逆转回去。如果它并不令人意外，就不会有人纳闷原因何在。如果不存在真正的备选方案，除了「我们做了显而易见的事」之外，便没有什么值得记录。

### 哪些情形符合

- **架构形态。**「我们采用 monorepo。」「写模型是事件溯源的，读模型投影到 Postgres 中。」
- **上下文之间的集成模式。**「订单与账单通过领域事件通信，而不是同步 HTTP。」
- **带有锁定风险的技术选型。**数据库、消息总线、认证提供方、部署目标。并非每个库都算：只包括那些换掉就要花上一个季度的库。
- **边界与范围决策。**「客户数据归 Customer 上下文所有；其他上下文仅通过 ID 引用它。」明确的「不做」与「做」同样有价值。
- **有意偏离常规路径。**「由于 X，我们使用手写 SQL 而不是 ORM。」任何一个理性读者都会默认相反做法的情形。这些记录能阻止下一位工程师把经过深思熟虑的东西「修正」掉。
- **代码中不可见的约束。**「出于合规要求，我们不能使用 AWS。」「由于合作方 API 契约的限制，响应时间必须低于 200ms。」
- **否决理由并不显而易见时的被否决备选方案。**如果你考虑过 GraphQL，又出于一些微妙的理由选择了 REST，就把它记录下来；否则半年后还会有人重新提议 GraphQL。
