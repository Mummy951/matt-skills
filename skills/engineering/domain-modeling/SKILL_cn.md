# 领域建模

在设计过程中主动构建并打磨项目的领域模型。这是一种*主动*的纪律：质疑术语、设想边界情况场景，并在术语与决策一旦定型时就立刻记入术语表与决策记录。（仅仅*阅读* `GLOSSARY.md` 来查词汇不属于本技能：那是任何技能都能做到的一行习惯动作。本技能面向的是你正在改动模型的时候，而不只是消费模型。）

## 文件结构

大多数仓库只有一个上下文：

```
/
├── GLOSSARY.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

如果根目录存在 `GLOSSARY-MAP.md`，说明该仓库包含多个上下文。该映射文件指明每个上下文所在位置：

```
/
├── GLOSSARY-MAP.md
├── docs/
│   └── adr/                          ← system-wide decisions
├── src/
│   ├── ordering/
│   │   ├── GLOSSARY.md
│   │   └── docs/adr/                 ← context-specific decisions
│   └── billing/
│       ├── GLOSSARY.md
│       └── docs/adr/
```

延迟创建文件：只有在确实有内容要记录时才创建。如果不存在 `GLOSSARY.md`，在第一个术语确定下来时再创建。如果不存在 `docs/adr/`，在第一个 ADR 产生需求时再创建。

## 会话期间

### 对照术语表提出质疑

当用户使用的术语与 `GLOSSARY.md` 中既有语言冲突时，立即指出。「你的术语表把『cancellation』定义为 X，但你这里似乎指的是 Y。到底是哪一个？」

### 打磨模糊的表述

当用户使用含糊或多义的术语时，提出一个精确的规范术语。「你说的『account』：指的是 Customer 还是 User？这两者是不同的东西。」

### 讨论具体场景

讨论领域关系时，用具体场景对其做压力测试。设想能够探查边界情况的场景，迫使用户明确概念之间的边界。

### 与代码交叉核对

当用户陈述某事物的工作方式时，检查代码是否与之相符。如果发现矛盾，把它摆出来：「你的代码取消的是整个 Orders，但你刚才说可以部分取消。哪一个才对？」

### 就地更新 GLOSSARY.md

术语一旦确定，就在原处更新 `GLOSSARY.md`。不要把这些积累起来批量处理：发生一条就记录一条。格式参见 [GLOSSARY-FORMAT.md](./GLOSSARY-FORMAT.md)。

`GLOSSARY.md` 中应当完全不包含实现细节。不要把 `GLOSSARY.md` 当作规格、草稿纸或实现决策的存放处。它就是一份术语表，仅此而已。

### 谨慎提供 ADR

只有在以下三个条件同时成立时，才提议创建 ADR：

1. **难以逆转**：日后改变主意的代价相当可观
2. **脱离上下文会令人困惑**：未来的读者会疑惑「他们当初为什么这么做？」
3. **是真实权衡的结果**：确实存在过真正的备选方案，并且你基于具体理由选择了其中一个

三个条件中只要缺一个，就跳过 ADR。格式参见 [ADR-FORMAT.md](./ADR-FORMAT.md)。
