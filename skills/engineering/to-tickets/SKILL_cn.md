# 转为工单

将一份计划、规格或对话拆分为一组**工单**：曳光弹式纵向切片，每个工单声明哪些工单**阻塞**它。

issue 跟踪器与分诊标签词汇表应当已经提供给你。如果没有，请提示用户运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 收集上下文

基于对话上下文中已有的内容开展工作。如果用户作为参数传入了一个引用（规格路径、issue 编号或 URL），获取并阅读其完整正文与评论。

### 2. 探查代码库（可选）

如果你尚未探查代码库，先去探查以理解代码的当前状态。工单标题与描述应使用项目的领域术语表词汇，并尊重你所触及区域内的 ADR。

寻找对代码进行前置重构（prefactor）的机会，让实现更容易。「先让变更变得容易，再去做这个容易的变更。」

### 3. 拟定纵向切片

将工作拆分为**曳光弹**工单。

<vertical-slice-rules>

- 每个切片贯穿每一层（schema、API、UI、测试），切出一条狭窄但完整的路径：是纵向切片，而不是只覆盖某一层的横向切片
- 一个完成的切片本身即可演示或验证
- 每个切片的规模应能放入单个全新的上下文窗口
- 任何前置重构都应先完成

</vertical-slice-rules>

为每个工单给出其**阻塞边**：在它开始之前必须完成的其他工单。没有阻塞项的工单可以立即开始。

**宽范围重构是纵向切片的例外。** **宽范围重构**是一次机械式变更（重命名一列、重新定义一个共享符号的类型），其**影响半径**扩散到整个代码库，因此单次编辑会同时破坏成千上万个调用点，没有任何纵向切片能够保持绿。不要强行把它做成曳光弹；按**扩–缩**的顺序来安排。先扩：在旧形式旁边新增新形式，使一切都不被破坏。然后按影响半径分批迁移调用点（按包、按目录），每一批各自成为一个工单，被「扩」工单阻塞；由于旧形式仍然存在，一批接一批地保持 CI 绿。最后缩：在没有任何调用方残留之后，删除旧形式，该工单被每一个迁移批次工单阻塞。当连各个批次都无法单独保持绿时，保留这一顺序，但让它们共享一条集成分支，全部阻塞最后一个集成并验证工单；绿只在那里承诺达成。

### 4. 向用户质询

以编号列表的形式呈现拟定的拆分方案。每个工单展示：

- **标题**：简短的描述性名称
- **被阻塞于**：必须先完成的其他工单（如有）
- **交付内容**：该工单使其可用的端到端行为

向用户询问：

- 粒度是否合适？（过粗 / 过细）
- 阻塞边是否正确：每个工单是否只依赖真正对其构成门槛的工单？
- 是否有工单应当合并或进一步拆分？

反复迭代，直到用户认可该拆分方案。

### 5. 将工单发布到已配置的跟踪器

发布已获认可的工单。**如何**发布取决于 `/setup-matt-pocock-skills` 配置的跟踪器；两种方式下工单本身相同，只有阻塞边的形式不同：

- **本地文件** → 在 `.scratch/<feature-slug>/issues/<NN>-<slug>.md` 下为每个工单写一个文件，按依赖顺序从 `01` 开始编号（阻塞项在前）。每个文件的「Blocked by」列出其所依赖的编号/标题。使用下面的单工单文件模板：每个文件一个工单，绝不要合并成单个文件。
- **真实 issue 跟踪器（GitHub、Linear、…）** → 按依赖顺序（阻塞项在前）每个工单发布一个 issue，以便每个工单的阻塞边可以引用真实标识符。平台有原生阻塞关系时使用它；否则将每个工单的「Blocked by」设置为阻塞它的 issue。如果来源是一个已有 issue，将每个工单作为其子 issue（按跟踪器文档的操作执行）。除非另有指示，否则打上 `ready-for-agent` 分诊标签；这些工单在设计上即可被智能体直接认领。

推进**前沿**：所有阻塞项都已完成的工单。对于一条纯线性链，这意味着自上而下。

不要关闭或修改任何父 issue。

无论哪种形式，都避免写具体文件路径或代码片段：它们很快就会过时。例外：如果某个原型产出了一段片段，能比文字更精确地编码某个决策（状态机、reducer、schema、类型结构），可将其内联，并简要注明它来自原型。裁剪到富含决策的部分，而不是可运行的演示，只保留重要片段。
