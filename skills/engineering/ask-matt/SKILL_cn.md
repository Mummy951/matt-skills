# 询问 Matt

你记不住每一个技能，那就来问。

在说明某个技能的作用、或建议跳过某一步骤之前，先阅读该技能的 SKILL.md：这里的摘要仅供定位参考。

**流程（flow）**是贯穿各技能的一条路径。大多数路径沿一条**主流程**运行，另有两条**入口匝道**汇入其中。其余内容要么是独立技能，要么是运行在底层的词汇层。

## 主流程：想法 → 交付

大多数工作走的路线。你有一个想法，想把它做出来。

1. **`/grill-with-docs`** 通过访谈打磨想法。只要你**在一个工作目录中工作**，就从这里开始：它是有状态的，会把学到的内容保留在 `GLOSSARY.md` 和 ADR 中。（没有工作目录？改用 `/grill-me`，见「独立技能」一节。两者运行同一个 `/grilling` 原语；`grill-with-docs` 会留下书面记录，因此只要有仓库可供留存，它就是两者中更优的选择。）
2. **分支：所有问题都能在对话中解决吗？** 如果某个问题需要可运行的答案（状态、业务逻辑、一个必须亲眼看到的 UI），就绕道经过一个原型，由双向的 **`/handoff`** 搭桥（原型位于它自己的目录中，这正是 `/handoff` 的用途；参见「阶段边界」）：
   - **`/handoff`** 交出，然后针对该文件开启一个新会话，
   - **`/prototype`** 用一次性代码回答该问题，
   - **`/handoff`** 带回你学到的内容，并在最初的想法线程中引用它。
3. **分支：这是一个跨多会话的构建吗？**
   - **是** → **`/to-spec`**（把线程转成一份规格），再用 **`/to-tickets`** 将其拆成曳光弹工单，每个工单声明自己的**阻塞边**。然后用以下两种方式之一处理工单：
     - 每个工单走 **`/implement`**，并在两个工单之间 **`/clear`** 上下文。在本地跟踪器上，每个工单对应 `.scratch/<feature>/issues/` 下的一个文件，按阻塞优先的顺序手工处理；在真正的跟踪器上，这些边变成原生的阻塞链接，因此任何阻塞项已完成的工单都可以被接手。每个工单都是自包含的，所以上一个工单的上下文用完即可丢弃。
     - 一次性处理整份规格，使用 **`/implement-spec`**。它把工单读成一张**任务图**，在就绪的**前沿**上并行运行实现者子代理，并把全部内容落到一条**集成分支**上。当你更想编排整个构建、而不是亲自驱动每个工单时，就用它。
   - **否** → 就在这里、在同一个上下文窗口中走 **`/implement`**。

   无论哪种方式，代码都通过驱动 **`/tdd`** 构建（一次一个红-绿切片），最后以 **`/code-review`** 收尾，这是对差异的双轴评审（标准 + 规格）。`/implement` 对每个工单都运行两者；`/implement-spec` 的各实现者各自驱动 `/tdd`，并在集成分支上运行一次 `/code-review`。当你只想测试先行地构建某个具体行为、而不需要完整规格时，可以单独使用 **`/tdd`**；当你想对照某个固定点评审一条分支或 PR 时，可以单独使用 **`/code-review`**。

   当工作以 PR（拉取请求）形式提交时，**`/pr`** 用来组织正文：展示变更的最小可视化、证明其可用的前后对比证据，以及单向门或双向门的判断。它由模型调用，因此智能体每次写 PR 时都会使用它。

4. **`/retro`** 闭环收尾。一次构建之后，尤其是走偏了的构建之后，它回顾整个会话，建议改动智能体的**环境**而非代码：导航指引、自动化检查、`/code-review` 所强制的编码标准、引导文件、工具链。机械性错误变成确定性检查；主观判断变成编码标准。下一次构建便从一个更好的环境起步。

### 上下文卫生

把第 1–3 步保持在**一个不中断的上下文窗口**中（在 `/to-tickets` 之后再压缩或清除），使深入质询、规格和工单都建立在同一套思路之上。此后每个 `/implement` 都从工单出发、全新开始。在清除之前，在被回顾的那个会话中运行 `/retro`；清除之后，则改为把它指向该会话的日志。

这方面的上限是**[smart zone（智能区）](https://www.aihero.dev/ai-coding-dictionary/smart-zone)**：在这个窗口内（最先进的模型约为 150k tokens），模型仍能清晰推理。如果会话在 `/to-tickets` 之前就接近该上限，不要在退化状态下硬撑；在最近的阶段边界执行 `/compact` 后继续（参见「阶段边界」）。

## 入口匝道

一种产生工作的起始处境，随后汇入主流程。

- **缺陷与请求堆积** → **`/triage`**。它让 issue 经过分诊角色流转，产出可直接交给智能体的 issue，之后由 **`/implement`** 接手。

  分诊只针对**并非你自己创建**的 issue：缺陷报告、进来的功能请求、任何原始到达的内容。`/to-tickets` 产出的工单已经可直接交给智能体，因此**不要对它们分诊**。

- **有东西坏了** → **`/diagnosing-bugs`**。用于疑难问题：一眼看不出的缺陷、偶发的不稳定、在两个已知良好状态之间悄悄混入的回归。在拥有**紧密反馈闭环**（一条已能在*这个*缺陷上变红的命令）之前，它拒绝空谈理论，然后用回归测试修复。修复落地后，在同一会话中运行 **`/retro`**，追问本可以如何预防该缺陷；如果真正的结论是没有好的接缝来锁定它，那就交给 **`/improve-codebase-architecture`**。

- **一项庞大而模糊的工作：全新项目或巨型功能构建，大到一个会话装不下** → **`/wayfinder`**，这里认知负担最重的流程。当从这里到目的地的路径尚不可见时，它在 issue 跟踪器上绘制一张由**决策工单**组成的**共享地图**，逐个解决它们，产出的是**决策而非交付物**，直到迷雾退去、路径清晰。**`/grill-with-docs`** 打磨的是你能在一个会话中把握的想法，而 wayfinder 面向的是你把握不了的想法；它更慢、更密，因此只留给这种场景，绝不要用于范围清晰的功能。

  地图清晰之后，**它负责交接，不负责构建**：在 **`/to-spec`** 处汇入主流程，把地图上相互关联的决策收敛成一份可构建的计划，然后照常走 `/to-tickets` 和 `/implement`。把地图直接接进 `/implement` 会跳过这次收敛，丢掉关联细节，因此只有当工作最终确实很小时，才直接进 `/implement`。

## 代码库健康

不是功能开发，只是维护保养。

- **`/improve-codebase-architecture`** 只要你有空就运行，让代码库保持适合智能体操作的状态。它会呈现**深化机会**；选中一个 _会生成一个想法_，你可以带到主流程的 `/grill-with-docs` 中。它是寻找候选对象的调研；**`/codebase-design`**（见下）则是你在上面设计所选对象的工作台。

## 底层词汇

两个由模型调用的参考技能，运行在其他技能*之下*，各自是其词汇的唯一权威来源。当问题出在**措辞**而非流程上时，可直接使用它们；也可以由上面的技能把它们引入。

- **`/domain-modeling`**：打磨项目的*领域*语言：质疑模糊的术语、消解一词多用（"account" 身兼三职），把难以逆转的决策记录为 ADR。它是 `/grill-with-docs` 所践行的主动纪律，用于让 `GLOSSARY.md` 保持为一份干净的术语表。
- **`/codebase-design`** 是深度模块词汇（模块、接口、深度、接缝、适配器、杠杆作用、局部性），用于设计一个模块的*形态*：在干净接缝处的小接口背后承载大量行为。`/tdd` 和 `/improve-codebase-architecture` 都使用这套词汇。

## 阶段边界

**阶段**是会话内的一块工作：深入质询、实现、QA。在两个阶段之间的**边界**上，你有五个选项，而在其中做选择是整张地图里最模糊的决策：

- **Continue（继续）**：原地不动。不付出代价，也不损失什么。
- **`/clear`**：清空窗口，适用于这里的内容对接下来的事毫无影响时。
- **`/handoff`** 写出一个可移植的 Markdown 文件。适用范围很窄：仅用于**新的运行框架**、**新目录**、**同事**，或**阶段中途**分出一个旁支任务。它换来的是可移植性。
- **子代理**：把一个范围严格限定的任务送到它自己的窗口，并收回一份报告。
- **`/compact`** 压缩当前上下文，并用它播种一个新会话。这是**默认**选项，位于决策树底部，而不是第一直觉。

阅读 [PHASE-BOUNDARIES.md](PHASE-BOUNDARIES.md) 了解有序决策树：五个问题、每个分支背后的推理，以及为什么一手资料成本使得 **Continue** 成为首先排除的选项。**在**边界处做决策；阶段中途则继续，或把剩余工作拆给子代理。

## 独立技能

完全位于主流程之外。

- **`/grill-me`**：与 `/grill-with-docs` 同样不留情面的访谈，但**无状态**：它不在本地保存任何内容，也不生成 `GLOSSARY.md`。当你**不在工作目录中工作**时使用它（打磨计划、设计、一篇文章，任何其下没有仓库的内容）。如果你在工作目录中，则改用 `/grill-with-docs`：它运行同样的访谈并留下书面记录，因此严格来说是更优的选择。
- **`/grilling`** 是访谈原语本身：轮次、前沿，事实是智能体的工作，决策是你的工作。`/grill-me` 和 `/grill-with-docs` 是两条具名入口，`/triage`、`/wayfinder` 和 `/improve-codebase-architecture` 都在内部运行它。只有当你想要不带任何包装的访谈时，才直接使用它。
- **`/prototype`** 是一个小型一次性程序，回答一个设计问题：这个状态模型感觉是否合适，或者这个 UI 应该长什么样。一次性是对代码写法的约束，而不是销毁它的承诺：答案会融入真实代码，原型本身作为**一手资料**保留在从 main 拉出的 `prototype/<name>` 分支上，并由实现 issue 指向它。它是主流程第 2 步中的绕道，但任何时候设计问题难以在纸面上解决，都可以使用它。
- **`/research`**：把阅读跑腿工作委派给**后台智能体**：它围绕**一手资料**调研一个问题，然后在仓库中留下一份带引用的 Markdown 文件。它阅读时你继续工作。它产出的文件要带入主流程的 `/grill-with-docs`，因为调研是滋养思路，而不是替代思路。
- **`/to-questionnaire`** 用于当阻碍你的东西不在你脑中或代码库里，而在**别人脑中**时：它为对方写一份问卷来填写。它是 `/grill-me` 的反向版本：它不就主题访谈你，而是就**发送**（发给谁、你需要拿回什么）访谈你，并把问题对准缺口。收回来的内容是 `/grill-with-docs` 或 `/to-spec` 的素材。
- **`/wizard`** 用于只有**人**才能完成的步骤：开通基础设施、配置凭证或 CI 密钥、在不熟悉的第三方控制台中点击操作、运行一次性迁移或切换。它生成一个交互式 bash 脚本，逐个打开 URL、采集每个值，并写入 `.env` 和 GitHub secrets，使这套流程不必每次都重新向智能体解释。它由模型调用，因此智能体一遇到只有你能越过的障碍就会使用它。如果智能体自己就能做，就应该自己做；这里面向的是确实需要人在环中的环节。
- **`/wait-what`** 用于纠正一条没有被理解到位的消息。在对话中途、任何其他技能内部使用它，智能体会结合你当时缺失的上下文，用平实的英语、借助 `GLOSSARY.md` 的词汇重新讲一遍刚才说的内容。它是事后补救；`/grill-with-docs` 是事前预防，因为早早就达成共识的共同语言，才是从源头阻止术语横飞的办法。
- **`/teach`**：跨多个会话学习一个概念，把当前目录作为有状态工作区。
- **`/writing-for-agents`** 是撰写智能体所消费文档的参考：技能、AGENTS.md、被指向的文档。
