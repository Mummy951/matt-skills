# 分诊

让项目 issue 跟踪器上的 issue 在一组由分诊角色构成的小型状态机中流转。

如果本仓库将外部 PR 也视为请求入口（见 issue 跟踪器配置），分诊同样覆盖它们：**PR 就是附带代码的 issue**，使用相同的角色、相同的状态和相同的状态机，仅有下文标注「for a PR」的少量差异。根据跟踪器配置，把单独出现的 `#42` 解析为某个 issue 或 PR。

分诊期间发布到 issue 跟踪器的每一条评论或 issue **都必须**以下列免责声明开头：

```
> *This was generated by AI during triage.*
```

## 参考文档

- [AGENT-BRIEF.md](AGENT-BRIEF.md)：如何编写长期有效的智能体简报
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)：`.out-of-scope/` 知识库的运作方式

## 角色

两个**分类**角色：

- `bug`（缺陷）：某个功能出了故障
- `enhancement`（增强）：新功能或改进

五个**状态**角色：

- `needs-triage`（待分诊）：等待维护者评估
- `needs-info`（待补充信息）：等待报告者提供更多信息
- `ready-for-agent`（可交智能体）：规格已完整，可交给离线智能体处理
- `ready-for-human`（待人工处理）：需要人工实现
- `wontfix`（不予修复）：不会采取行动

对于 PR，相同状态结合附带的代码来解读：`ready-for-agent` 表示已附上简报，智能体应在差异上迈出下一步；`ready-for-human` 表示已准备好由人工合并。

每个完成分诊的 issue 都应恰好带有一个分类角色和一个状态角色。如果状态角色相互冲突，先标记出来并询问维护者，再做其他任何处理。

以上是规范的角色名。issue 跟踪器中实际使用的标签字符串可能不同。映射关系应当已经提供给你；如果没有，请告知用户运行 `/setup-matt-pocock-skills`。

状态流转：未打标签的 issue 通常先进入 `needs-triage`；之后可流转到 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。报告者回复后，`needs-info` 退回 `needs-triage`。维护者随时可以覆盖上述规则；看起来异常的流转要先标记并询问，再继续操作。

## 调用方式

维护者调用 `/triage`，用自然语言描述需求。理解请求并采取行动。示例：

- 「给我看看所有需要我关注的内容」
- 「我们看看 #42」（issue 或 PR）
- 「把 #42 移到 ready-for-agent」
- 「有哪些已经准备好可以交给智能体接手？」

## 展示需要关注的内容

查询 issue 跟踪器，按时间从旧到新，分三个分组呈现：

1. **未打标签**：从未分诊。
2. **`needs-triage`**：正在评估中。
3. **`needs-info` 且自上次分诊备注以来报告者有新动态**：需要重新评估。

当 PR 属于分诊范围时，把外部 PR 一并纳入这些分组，并在每条行尾标注 `[PR]` 或 `[issue]`。发现机制只列出*外部* PR（谁算外部由跟踪器配置定义），因此协作者正在进行中的 PR 不属于分诊工作。该过滤仅用于发现阶段；被明确点名的 PR 无论作者是谁，都要进行分诊。

给出数量统计，并为每条提供一行摘要。由维护者选择。

## 对指定 issue 或 PR 进行分诊

1. **收集上下文。** 阅读完整的 issue 或 PR（正文、评论、标签、作者、日期；PR 还需阅读差异）。解析已有的分诊备注，避免重复询问已经解决的问题。借助项目的领域术语表探索代码库，并尊重相关领域的 ADR。对照代码库做两项检查：(a) **冗余性**：按领域概念（而不只是请求中的措辞）搜索所请求行为是否已有现成实现，并报告你检索过的位置。若已找到，则属于「已实现」的 `wontfix`（进入第 5 步）。(b) **既往拒绝记录**：阅读 `.out-of-scope/*.md`，找出任何与本请求相似的条目。

2. **给出建议。** 向维护者说明你推荐的分类与状态及理由，并附上与请求相关的简要代码库概况（包括是否已经实现）。等待指示。

3. **核实陈述。** 在深入质询之前，先检查陈述是否成立。对于 bug，按报告者的步骤复现；对于 PR，确认差异与其所述相符：检出代码，运行相关测试或命令。报告结果：已确认（附代码路径）、复现失败，或信息不足（这是 `needs-info` 的强烈信号）。经过确认的核实能让智能体简报扎实得多。

4. **深入质询（如需要）。** 如果请求需要进一步充实，两次调用 Skill 工具，分别对应「grilling」和「domain-modeling」，一轮问题一轮问题地把它质询成型；随着决策落定，同步精炼领域术语并更新 `GLOSSARY.md`/ADR。

5. **应用结论：**
   - `ready-for-agent`：发布一条智能体简报评论（见 [AGENT-BRIEF.md](AGENT-BRIEF.md)）。
   - `ready-for-human`：结构与智能体简报相同，但需说明为何不能委派（需要主观判断、外部访问、设计决策、手工测试）。
   - `needs-info`：发布分诊备注（模板见下）。
   - 对于 `wontfix`，关闭该 issue，评论内容取决于*原因*：
     - **已实现**：该改动在代码库中已存在。指明它所在的位置；**不要**写入 `.out-of-scope/`（该知识库用于*被拒绝*的请求，而非已构建完成的请求）。
     - **拒绝（bug）**：给出礼貌的解释，然后关闭。
     - **拒绝（enhancement）**：写入 `.out-of-scope/`，在评论中链接到该条目，然后关闭（见 [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)）。
   - `needs-triage`：应用该角色。若已有部分进展，可附评论。

## 快速覆盖状态

如果维护者说「把 #42 移到 ready-for-agent」，信任他们并直接应用该角色。先确认你将要做的操作（角色变更、评论、关闭），然后执行。跳过深入质询。若未经过质询环节就转入 `ready-for-agent`，询问是否需要编写智能体简报。

## needs-info 模板

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

把质询过程中已确定的所有内容归入模板中的「established so far」项下，以免工作成果丢失。问题必须具体、可执行，不能是「请提供更多信息」这类笼统说法。

## 恢复上一次会话

如果 issue 或 PR 上已有既往分诊备注，先阅读它们，检查报告者是否已回答任何未决问题，并在继续之前呈现更新后的全貌。不要重复询问已解决的问题。
