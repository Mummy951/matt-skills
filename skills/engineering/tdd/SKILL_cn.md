# 测试驱动开发

TDD 是红 → 绿的循环。本技能是让该循环产出值得保留的测试的参考依据：什么是好测试、测试放在哪里、有哪些反模式，以及循环的规则。每一节都适用于每一轮循环：在循环之前和循环过程中查阅，而不是事后再看。

在探索代码库时，阅读 `GLOSSARY.md`（如果存在），使测试命名和接口词汇与项目的领域语言保持一致，并尊重你所触及区域内的 ADR。

## 什么是好测试

测试通过公开接口验证行为，而不是实现细节。代码可以彻底改变，测试不应随之改变。好测试读起来像一份规格："user can checkout with valid cart" 准确告诉你存在什么能力，而且它能在重构中存活，因为它不关心内部结构。

示例见 [tests.md](tests.md)，mock 规范见 [mocking.md](mocking.md)。

## 接缝：测试放在哪里

**接缝**是你进行测试的公开边界：在这个接口处观察行为，而不探入内部。测试位于接缝处，绝不对着内部实现编写。

**只在预先约定的接缝处测试。** 在编写任何测试之前，先写下要测试的接缝，并与用户确认。未经验收的接缝上不写任何测试。你不可能测试一切，因此预先约定接缝，才能把测试精力投放到关键路径和复杂逻辑上，而不是覆盖每一个边界情况。

询问："What's the public interface, and which seams should we test?" 为每个提出的接缝写一行说明，写明它能捕捉什么、又会遗漏什么。

当该接口的形态本身尚有疑问（模块有多深、接缝应位于何处、接口应暴露什么）时，调用 Skill 工具，传入 "codebase-design" 以获取相关词汇。它是 module、interface、depth、seam、adapter、leverage 和 locality 等术语的共享来源；它是一份供查阅的参考，而不是一个需要运行的会话。

## 反模式

- **与实现耦合**：mock 内部协作者，测试私有方法，或通过旁路上的渠道进行验证（查询数据库而不是使用接口）。典型征兆：重构时测试挂掉，但行为并未改变。
- **同义反复**：断言以与代码相同的方式重新计算期望值（`expect(add(a, b)).toBe(a + b)`、以同样方式手工推导的快照、断言某个常量等于它自身），因此它按构造必然通过，永远不可能与代码相左。期望值必须来自独立的事实来源：已知正确的字面量、演算示例或规格。
- **水平切分**：先写完所有测试，再写所有实现。成批测试验证的是_想象中_的行为：你测试的是事物的_形态_，而不是面向用户的行为；测试会对真实变化变得不敏感；而且你在理解实现之前就先锁定了测试结构。应改为按**垂直切片**推进：一个测试 → 一个实现 → 重复，每个测试都是一颗**曳光弹**，呼应上一轮循环所教给你的东西。

## 循环的规则

- **先红后绿。** 先写失败的测试，再写刚好能让它通过的代码。不要预判未来的测试，也不要添加投机性的功能。
- **每次只做一个切片。** 每一轮循环：一个接缝、一个测试、一个最小实现。
- **重构不属于循环。** 重构属于评审阶段（见 `code-review` 技能），而不是红 → 绿的实现循环。
